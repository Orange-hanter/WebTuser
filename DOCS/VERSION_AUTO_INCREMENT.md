# Auto Version Increment

## 🚀 Как работает автоинкремент версий

Система автоматически инкрементирует версии на основе conventional commits и создаёт git теги.

### Semantic Versioning (SemVer)

- **MAJOR.MINOR.PATCH** (например: 1.2.3)
- **MAJOR**: Несовместимые изменения API
- **MINOR**: Добавление новой функциональности
- **PATCH**: Исправление багов

## 📝 Conventional Commits

Версия инкрементируется на основе типа коммита:

| Тип коммита | Инкремент | Пример |
|-------------|-----------|--------|
| `fix:` | PATCH | `fix: исправить баг в логине` → 1.2.3 → 1.2.4 |
| `feat:` | MINOR | `feat: добавить новый компонент` → 1.2.3 → 1.3.0 |
| `BREAKING CHANGE` | MAJOR | `feat: переписать API BREAKING CHANGE` → 1.2.3 → 2.0.0 |
| Другие | PATCH | `refactor: оптимизировать код` → 1.2.3 → 1.2.4 |

## 🔄 Workflow процесса

```
Push to develop/main
    ↓
lint → build → version → deploy
                ↓
        Создаёт git tag (v1.2.4)
        Создаёт GitHub release
        Обновляет package.json
```

## 🛠️ Ручное управление версиями

Используйте скрипт `scripts/version.sh`:

```bash
# Показать текущую версию
./scripts/version.sh current

# Инкрементировать patch версию (1.2.3 → 1.2.4)
./scripts/version.sh patch

# Инкрементировать minor версию (1.2.3 → 1.3.0)
./scripts/version.sh minor

# Инкрементировать major версию (1.2.3 → 2.0.0)
./scripts/version.sh major
```

## 📋 Примеры коммитов

### Patch (исправления)
```
fix: исправить валидацию email в форме регистрации
fix: починить отображение ошибок в мобильной версии
```

### Minor (новая функциональность)
```
feat: добавить экспорт данных в CSV
feat: реализовать поиск по событиям
```

### Major (ломающие изменения)
```
feat: переписать API авторизации BREAKING CHANGE
refactor: изменить структуру компонентов BREAKING CHANGE
```

## 🎯 Автоматические релизы

При каждом push в `develop` или `main`:
- ✅ Автоматически определяется тип изменения
- ✅ Инкрементируется версия в `package.json`
- ✅ Создаётся git tag (`v1.2.4`)
- ✅ Создаётся GitHub release с описанием
- ✅ Деплой происходит с новой версией

## 📊 История версий

Посмотреть все версии:
```bash
git tag --list 'v*'
```

Посмотреть последние релизы:
```bash
gh release list
```

## ⚙️ Настройка

### Отключение автоинкремента
Если нужно временно отключить:
```yaml
# В .github/workflows/ci-cd.yml
version:
  if: false  # Отключить автоинкремент
```

### Кастомная логика
Измените логику определения типа версии в job `version`:
```yaml
- name: Determine version bump
  run: |
    # Ваша логика определения типа версии
    # Например, на основе labels в PR
```

## 🔍 Мониторинг

- **Tags**: `git tag` - список всех версий
- **Releases**: GitHub → Releases - история релизов
- **Package.json**: Текущая версия в коде
- **Workflow logs**: Детали процесса инкремента

## 🚨 Важные замечания

1. **Conventional commits обязательны** для правильной работы автоинкремента
2. **Git tags создаются автоматически** - не создавайте их вручную
3. **Releases создаются автоматически** с описанием изменений
4. **Deploy использует новую версию** для отслеживания

## 🐛 Troubleshooting

### Версия не инкрементируется
- Проверьте формат коммита (conventional commits)
- Убедитесь что push в `develop` или `main`

### Ошибка создания тега
- Проверьте права GitHub token
- Убедитесь что тег с такой версией не существует

### Релиз не создался
- Проверьте настройки GitHub repository
- Убедитесь что `GITHUB_TOKEN` имеет права на создание релизов
